## 機能候補

優先度の高い順。「規模」は実装からテスト・README 更新までの目安。【要望あり】はユーザーから明示的に要望があった項目。

### 1. 複数 CSV 形式への対応(規模: 中〜大)

- 銀行口座 CSV の取込(#17)で card / bank の 2 プロファイルを `csv_parser.csv_profiles()` に切り出し済み。ここではカード会社ごとの差分を足す
- カード会社ごとのパーサープロファイル(メタ行のキー、ヘッダー行の目印、列名候補、文字コード優先順)を定義し、CSV の内容から自動選択する
- データ構造への影響: `imports` にプロファイル名の列を追加すると追跡しやすい(任意)。`transactions.card` はカード名で区別できる
- 重複判定は (row_key, カード名) なので別カードの同一明細は別扱いになる。プロファイル間で `card` の表記を揃えること

### 2. バックアップからの復元(規模: 小)

- `data/backup/` の世代一覧を画面に出し、選んだ世代を正本に戻す(戻す前に現在の正本も世代バックアップに退避)
- データ構造への影響: なし
- 注意: 復元中に他のリクエストが保存しないよう、`ExcelRepository.lock` の中で行う

### 3. 明細の単体削除(規模: 小)

- 編集画面から取込明細を 1 件だけ削除する(内訳も同時に削除)。誤取込や返品の整理用
- 手動明細の削除(`services/manual_entries.py` の `delete_manual_transaction`)は実装済み。取込明細は現在 2 か所で制限しているので、許可する場合は両方を外す: `delete_manual_transaction` の `not tx.is_manual_entry` チェック(サーバー側)と、`edit.html` の削除欄の表示条件 `{% if tx.is_manual_entry %}`。あわせて `test_imported_transaction_cannot_be_deleted` / `test_delete_manual_transaction_rejects_imported` を更新する
- データ構造への影響: なし
- 注意: 削除した明細の `row_key` が消えるため、同じ CSV を再取込すると再び新規として入る。削除を「除外」として `row_key` だけ残す設計にするなら `transactions` に `excluded` 列が必要(要検討)

## 対象外(MVP 方針を継続)

SQL / SQLite、Docker、WSL 前提、n8n、ユーザー認証(アカウント管理。自宅 LAN 向けの起動ごとの PIN は除く)、外部公開(インターネット側への公開。自宅 LAN 内は除く)、Dropbox API、Dropbox → Smart Ledger の逆同期、
iOS ネイティブアプリ、銀行・カード API 連携、スクレイピング、複雑な予算管理、機械学習モデルの自前学習。
